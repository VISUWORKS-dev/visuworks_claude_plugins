# TDD 사이클 — 한 번에 항목 하나

spec 문서의 `## 테스트 목록`에서 **항목 하나**를 골라 아래 순서로 통과시킨다.
두 항목을 같이 하지 않는다 — 실패했을 때 어느 쪽 탓인지 모르게 된다.

오케스트레이터는 **모듈 묶음**(`### M1` 아래 항목들) 단위로 "go"를 보낸다. 받은 묶음 안의
항목을 순서대로 한 사이클씩 통과시키고, 묶음이 끝나면 보고하고 멈춘다. 다음 묶음으로 넘어가지
않는다 — 오케스트레이터가 경계면 검증(`3c`)을 거친 뒤 보낸다.

`check_cmd`·`tests_dir`·`contract_tests_dir`는 `.claude/harness.config.json`의 값이다.

## 사이클

1. **실패 테스트를 쓴다.** 항목의 기대값을 그대로 단정문으로 옮긴다.
2. **실패를 확인한다.** 돌려서 실제로 실패하는 것을 본다.
   여기서 통과하면 그 테스트는 아무것도 검증하지 않는다 — 다시 쓴다.
3. **최소 구현.** 그 테스트를 통과시키는 가장 작은 코드. 다음 항목을 미리 만들지 않는다.
4. **전체 테스트를 돌린다.** `check_cmd`. 다른 항목을 깨뜨렸으면 거기서 멈추고 고친다.
5. **필요하면 구조 정리.** 중복이 눈에 보일 때만. 안 보이면 넘어간다.

## 커밋 — 기능과 구조를 섞지 않는다

| 커밋 | 언제 | 형식 |
|---|---|---|
| 기능 | 테스트 목록 항목을 통과시켰을 때 | `[behavioral] T<n>[,T<m>]: <설명>` |
| 구조 | 동작을 바꾸지 않고 정리했을 때 | `[structural] <설명>` |

**한 커밋에 섞지 않는다.** 섞이면 리뷰에서 "동작이 바뀐 것인가"를 판단할 수 없고,
되돌릴 때 기능과 정리가 함께 날아간다. 구조 정리를 먼저 하고 기능을 얹는 것이
반대 순서보다 쉽다(Tidy First).

**같은 묶음 안의 항목은 한 커밋에 묶을 수 있다**(`[behavioral] T1,T2: ...`). 사이클은 항목
하나씩 돌리되, 커밋은 의미 단위로 모은다. **묶음을 넘어서 묶지 않는다** — 3c 검증과 되돌리기가
묶음 단위로 일어난다.

`[structural]` 커밋은 `tests_dir`를 건드릴 수 없다. git hook이 막는다 —
테스트가 바뀌면 그것은 동작 변경이다.

## 하지 않는 것

**테스트 목록에 없는 기능을 만들지 않는다.** 필요해 보이면 구현하지 않고
보고의 `questions:`에 적는다. 목록은 사람이 승인한 범위다 — 늘리는 것은 사람의 몫이다.

**테스트 목록의 기대값을 바꾸지 않는다.** 틀렸다고 판단되면 **구현을 멈추고**
`questions:`로 보고한다. 기대값을 고쳐 통과시키는 것은 판정 기준을 구현에 맞추는 것이고,
그 순간 테스트는 아무것도 막지 못한다.

**계약 테스트(`contract_tests_dir`)를 고치지 않는다.** 실패하면 구현을 고친다.
계약 자체가 틀렸다고 판단되면 `contract-guardian`에게 요청한다.

**같은 항목에서 3회 실패하면 멈춘다.** `result: blocked`으로 보고하고
무엇을 시도했고 왜 안 됐는지 적는다. 4회째는 같은 실패를 반복할 뿐이다.

## 최종 보고

```
item: M1 (T1,T2,T3)
result: pass | fail | blocked
evidence: 실행한 명령과 결과 요약, 커밋 해시
questions: (있을 때만)
next: (fail일 때)
```

`evidence`는 실제 출력이다. "테스트 통과함"은 주장이지 증거가 아니다 —
`check_cmd` 결과를 그대로 옮긴다.
