issue-harness 0.2.9 · 사용자 안내

이슈 하나를 계획부터 로컬 머지까지

issue-harness는 GitHub 이슈 하나를 받아 계획, 계약 확정, 테스트 목록 TDD 구현, 두 단계 검증, 로컬 머지까지 여러 에이전트에게 나눠 맡깁니다. 목표는 단계와 단계가 이어지는 곳의 어긋남을 마감 직전이 아니라 모듈을 만든 직후에 잡는 것입니다.

이 문서는 안내입니다규칙의 정본은 플러그인의 스킬과 에이전트 정의입니다. 이 페이지는 0.2.9 기준으로 그 규칙을 풀어 쓴 것이라, 둘이 다르면 스킬이 맞습니다.

한눈에

사람은 세 번 개입합니다. 계획 승인, 막혔을 때의 판단, 마지막 push입니다. 나머지는 오케스트레이터(이 스킬을 실행한 Claude 세션)가 에이전트를 부르고 결과를 판정하며 진행합니다.

issue-planner

이슈를 읽고 spec(작업 계획과 테스트 목록)을 씁니다. 파일 하나만 쓰고 코드는 건드리지 않습니다.

contract-guardian

단계 사이에 오가는 데이터의 모양(필드, 상태값, 경로)을 정하는 계약의 주인입니다. full 경로에서만 부릅니다.

implementer

격리된 워크트리에서 테스트 목록을 한 항목씩 TDD로 통과시키고 커밋합니다. push와 머지는 하지 않습니다.

integration-qa

계약 테스트를 구현보다 먼저 쓰고, 이어 붙이는 곳을 검증합니다. 제품 코드는 고치지 않습니다.

시작은 이슈 12 시작처럼 말하면 됩니다. 프로젝트에 .claude/harness.config.json이 없으면 먼저 /issue-harness:init으로 설정을 깝니다.

먼저 알아 둘 말

spec
<spec_dir>/issue-<N>.md. 이슈를 어떻게 만들고 무엇으로 확인할지 적은 계획. 테스트 목록(T1, T2…)과 모듈 묶음(M1, M2…)이 들어 있습니다.
계약
생산자와 소비자가 주고받는 데이터의 약속. 필드 이름, 타입, 상태값 문자열, 산출물 경로.
정본
같은 내용이 여러 곳에 있을 때 기준이 되는 단 한 곳. 진행 상황의 정본은 git 로그입니다.
묶음과 go
구현자에게 한 번에 맡기는 테스트 항목 묶음. 오케스트레이터가 묶음마다 “go”를 보냅니다.
단정
테스트 안의 assert. 결과가 반드시 이래야 한다고 못 박는 한 줄입니다.
워크트리
같은 저장소를 다른 폴더에 하나 더 펼친 작업 공간. 구현자만 씁니다.

full과 light — 경로부터 고릅니다

모든 이슈에 같은 강도의 검증을 걸면 비용이 너무 큽니다. 그래서 계약이 바뀌는지를 기준으로 두 경로로 나눕니다. 판정이 애매하면 full입니다.

경로어떤 이슈생략하는 것
full계약을 새로 만들거나 바꾸는 이슈, 여러 단계를 잇는 이슈없음
light화면 수정, 기존 계약만 쓰는 이슈, 문서·설정계약 확정(3a), 계약 테스트 선작성(3a-test), 묶음별 점검(3c), 무컨텍스트 검증(4a). 팀도 꾸리지 않습니다
 
flowchart LR
  A["이슈 읽기"] --> B{"계약을 새로 만들거나
바꾸는가?"}
  B -- "예 / 애매함" --> F["full 경로"]
  B -- "아니오" --> L["light 경로"]
  L -. "진행 중 계약 변경이 필요해짐" .-> F

light로 가다가 계약을 바꿔야 하면 full로 올립니다. 끝난 묶음은 먼저 머지하고, 남은 묶음은 새 구현자가 맡습니다.

함께 정하는 것이 PR 줄입니다. PR: <basic|review|full> · push <자동|사람> 형식으로 spec 머리에 적고, 계획 승인 때 사람이 확정합니다. 확정 전에는 push하지 않습니다.

사람 승인 게이트 (2b)테스트 목록은 반드시 사람이 승인합니다. 구현자는 기대값을 바꿀 수 없어서, 승인 없이 들어가면 아무도 확정하지 않은 기대값이 정본이 됩니다. 답이 비어 있는 질문이 남으면 구현으로 넘어가지 않습니다.

Phase 3 · 구현

full — 계약을 먼저 고정합니다

계약이 바뀌었으면 integration-qa는 계약 커밋의 변경 내용으로 기존 계약 테스트를 찾아 같은 커밋에서 함께 고칩니다. 옛 계약을 단정하는 단위 테스트는 목록만 보고하고, 구현자가 go의 [주의]로 받아 고칩니다. 테스트가 구현에 거는 전제(가짜를 끼우는 지점 등)도 같은 길로 갑니다.

3a-test에서 보는 것 — 실패의 개수가 아니라 원인

작성 직후 결과판정
구현이 없어서 실패 (함수 없음, 계약 값과 다름, 제품 CLI의 실패 exit code)정상 — 넘어갑니다
통과빈 테스트 — 다시 씁니다
테스트가 직접 만든 가짜 스크립트의 문법·import 오류로 실패테스트 결함 — 다시 씁니다
가짜 함수가 계약 시그니처보다 좁게 받음 (lambda *args) — 지금은 「구현 없음」으로 보여도 키워드로 부르는 구현에서 실패테스트 결함 — 다시 씁니다

3c와 최종 검증에서 보는 것 — 기대값의 출처

새로 쓰거나 바꾼 단정마다 기대값이 구현과 무관하게 정해졌는지 읽어서 확인합니다. 리터럴, 계약에 적힌 값, 변경 전에 잰 값이면 유효합니다. 구현 결과로 기대값을 계산하거나(변경 뒤에 센 행 수), 양쪽이 같은 출처라 늘 참인 비교는 무효입니다. 테스트만 바뀐 묶음도 3c를 거칩니다.

구현자에게 가는 지시 (go)

계약은 절 위치와 원문 인용으로 넘깁니다. 한 줄 요약을 붙여도 어느 절을 볼지 알려 주는 색인일 뿐이고, 기대값은 원문에서 읽습니다.

Phase 5 · 보고

오케스트레이터가 완료된 단계마다 증거(커밋 해시, check_cmd 결과, 검증 보고서 경로, PR 링크)를 달아 보고합니다. PR 줄이 push 자동이면 오케스트레이터가 push와 PR까지 하고, push 사람이면 실행할 명령만 출력합니다. 역할 에이전트는 어느 경우에도 push하지 않습니다.

왜 이렇게 됐나 — 결정과 이력

지금의 절차는 처음부터 설계된 것이 아니라, 실제 이슈를 돌리다 생긴 사고를 하나씩 막으며 쌓였습니다. 괄호 안 번호는 이 저장소의 이슈·PR입니다.

처음부터 있던 원칙

원칙이유
이슈 = 워크트리 = PR구현자를 격리된 폴더에서 돌려야 오케스트레이터와 구현이 서로의 작업을 덮어쓰지 않습니다.
계약 테스트는 QA가 먼저구현자가 쓴 테스트는 자기 설계에 맞춰집니다. 구현이 틀리면 테스트도 같이 틀려 통과합니다. 계약도 구현도 소유하지 않은 제3자가 써야 독립적인 기준이 됩니다.
검증자는 제품 코드 금지검증자가 고치면 자기 구현을 자기가 검증하는 구조가 됩니다.
계약 TDD는 형태만LLM 출력처럼 비결정적인 내용은 단정할 수 없습니다. 항목 수, 필수 필드, 상태값처럼 소비자가 읽다가 터지는 것만 겁니다.
