# 평가 4회차 — 2026-11-04, 단위 테스트 사전 검토 제안의 전제 측정

PR #53 리뷰에서 나온 제안(고위험 변경만 「구현자 Red → QA 사전 검토 → Green」)을 넣기 전에 그 전제를 쟀다.
전제는 둘이다 — 사후 검토(3c)가 구현자가 쓴 약한 단위 테스트를 놓친다, spec이 모호하면 구현자가 테스트 범위를 좁힌다.
하네스 정의는 0.2.11 그대로 돌렸다(바꾸지 않음).

## 구성

- M1 — integration-qa `3c`. 1회차 샌드박스(`orders-app` 이슈 #12) M1 묶음을 계약대로 구현한 워크트리에 약한 단위 테스트 2개를 심었다.
  두 테스트 모두 일부러 틀리게 바꾼 구현에서도 통과하는 것을 먼저 확인했다
  - W1 `비가역` T2 — 거절된 환불 테스트가 `status`만 단정, `refund_reason is None`을 단정하지 않음
  - W2 `로직` T1 — 정규화 표가 spec 4사례 중 2개(`"  파손 "`, `""`)만. 공백만·201자 누락
- M2 — issue-planner `2a`. 새 이슈 #13(승인된 환불을 PG사에 요청하고 정산 원장에 기록)을 C1~C3만 주고 사례는 주지 않았다.
  `비가역` 항목에 중복 실행·부분 기록·경계값이 항목이나 `open_questions`로 들어가는지 봤다
- opus·sonnet 각 2회. 실행자는 작업 트리의 정의 파일을 읽게 한 general-purpose 에이전트. 채점은 실행자와 다른 인스턴스

## 판정

- 두 전제 모두 이번 측정 범위에서 재현되지 않음. 사전 검토 단계·3c 점검표 보강을 지금 넣을 근거 없음
- #30 회고의 「사례부터, 안 될 때만 장치」에 따라 보류. 사후 검토가 놓친 실제 사례가 생기면 다시 본다

## 한계

- 심은 약점은 둘 다 spec 목록과 대조하면 보이는 종류다. 목록 밖에서 구현자가 쓰는 단위 테스트(외부 호출 분기·실패 경로)는 재지 않았다.
- 3c 프롬프트에 「이번 묶음 커밋」을 직접 줬다. 약한 테스트가 큰 diff에 섞였을 때의 발견율은 모른다.
- M2 경계값 판정은 항목과 질문을 같이 셌다. 질문으로 올린 사례가 2b에서 실제 항목이 되는지는 사람 답에 달렸다.
- 보고 파일 쓰기가 일부 실행에서 거부돼 응답 본문으로 받은 보고로 채점했다(이전 회차와 같은 환경 문제).
