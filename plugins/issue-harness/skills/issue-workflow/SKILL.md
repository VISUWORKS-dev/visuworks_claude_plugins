# Issue Workflow — 이슈 = 워크트리 = PR

작업 단위는 **GitHub 이슈 하나**다. 이슈 하나에 워크트리 하나, PR 하나가 대응한다.

`<키>`는 `.claude/harness.config.json`의 값이다. 이슈 간 선후 관계(의존 순서)는 프로젝트마다
다르므로 `domain_skills.workflow`가 가리키는 스킬에 있다.

## 전체 흐름

```
이슈 확인 → 이슈 브랜치 생성 → 계획(spec 문서) → 핸드오프 커밋
   → 워크트리 생성 → 구현·커밋 → 검증 → [오케스트레이터] 로컬 머지 → [PR 줄대로] push·PR → [사람] 기본 브랜치 머지
```

## 1. 이슈 브랜치

| 브랜치 | 누가·어떻게 | 예 |
|---|---|---|
| 이슈 브랜치 | 사람/오케스트레이터 — `branch_pattern`대로. `gh issue develop`도 된다 | `12-order-export` |
| 워크트리 브랜치 | Claude Code가 자동 생성 (4절) — 이름 지정 불가 | `worktree-agent-<id>` |

워크트리 브랜치 이름에는 이슈 번호가 없다. 이 이슈의 spec 커밋을 포함하는 `worktree-agent-*` 브랜치가
이 이슈의 것이다(`git branch --contains <spec 커밋> --list 'worktree-agent-*'`).

### 범위 산정 — 하네스 밖 작업

하네스 없이 이슈를 직접 고칠 때도 브랜치·수정 전에 범위와 PR 줄을 사람에게 확인받는다.
바꿀 파일·단계를 먼저 보이고, 경로·PR 모드·push는 `issue-harness:issue-harness` 「시작 설정 질문」대로
`AskUserQuestion` 질문 3개로 따로 묻는다(형식은 같은 스킬 「PR 줄」). 확인 전 PR 줄은 미확정이다 — push하지 않는다.
확정 뒤 그 작업을 하는 에이전트가 오케스트레이터다 — 커밋·검증 뒤 이 줄대로 `pr-writing`을 끝까지 따른다.

## 2. 계획 — spec 문서

구현 전에 `<spec_dir>/issue-<번호>.md`를 만든다. `issue-harness:issue-planner`가 쓴다.

**왜 먼저 쓰는가:** 이슈들이 스키마·경로·상태값으로 연결되어 있으면, 계획 없이 착수한
구현자가 계약을 임의로 정하고 그것을 읽는 다른 이슈가 나중에 틀어진다.

**추측으로 채우지 않는다.** 모르는 항목은 `TODO(확인필요)`로 남긴다. 추측으로 채운 계획은
그럴듯해 보이므로 아무도 다시 묻지 않는다 — 그게 가장 비싼 실수다.

**`## 테스트 목록`을 반드시 포함한다.** 구현자는 이 목록의 항목을 하나씩 TDD로
통과시키고(`issue-harness:tdd-cycle`) 목록 밖을 만들지 않는다. 사람 승인 후에 구현에 들어간다.

## 3. 핸드오프 커밋 — 워크트리 생성 직전

워크트리는 **커밋 기준의 깨끗한 체크아웃**이다. 커밋되지 않은 파일과 gitignore된 파일은
따라오지 않는다.

**spec은 tracked다.** `docs :` 커밋으로 올리면 워크트리에 그대로 따라온다:

```bash
git add <spec_dir>/issue-<N>.md
git commit -m "docs : 이슈 #<N> spec — 테스트 목록 <n>항목"
```

**런타임 상태(`.harness/`)는 gitignore되어 따라오지 않는다.** 구현자는 상태 파일을
읽지도 쓰지도 않는다 — 오케스트레이터가 이번 묶음·계약(절 위치 + 원문 인용)·이전 실패 원인을
프롬프트에 담아 넘기고(`issue-harness:issue-harness` Phase 3 템플릿), 돌아온 보고를 primary의
`state.json`에 반영한다. 경과는 훅이 primary에 기록한다 (`issue-harness:harness-state`).

제품 코드에 전달할 것이 있으면 그것만 커밋한다:

```bash
git add <전달할 파일>
git commit -m "docs : 이슈 #<번호> <전달 내용>"
```

계약·계약 테스트의 커밋 메시지는 `issue-harness:issue-harness` 「full — `3a-contract` → `3a-test`」.

## 4. 워크트리 생성 · 구현자 실행

오케스트레이터가 **`Agent` 툴에 `isolation: "worktree"`를 줘서** 부른다. 워크트리 생성과
구현자 기동이 한 번에 되고, 에이전트 정의가 그대로 적용된다.

```
Agent(
  subagent_type: "issue-harness:implementer",
  isolation: "worktree",
  name: "impl-<번호>",
  run_in_background: true,
  model: <models.implement>,
  prompt: "<issue-harness:issue-harness Phase 3 템플릿 — 첫 모듈 묶음>"
)
```

- **기준점은 primary의 현재 HEAD다** — `.claude/settings.json`의 `worktree.baseRef: "head"`.
  부르기 직전에 `git branch --show-current`가 이슈 브랜치이고 핸드오프 커밋이 HEAD에 있는지
  확인한다. 이 설정이 없으면 기본 브랜치에서 갈라져 **핸드오프 커밋이 없는 워크트리**가 된다.
  플러그인은 이 설정을 넣을 수 없다 — `/issue-harness:init`이 안내한다.
- **위치·브랜치는 자동이다** — `.claude/worktrees/agent-<id>/`, `worktree-agent-<id>`.
  완료 알림에 경로와 브랜치가 함께 온다. 나중에는 `git worktree list`로 다시 찾는다.
- **다음 단위는 `SendMessage(to: "impl-<번호>")`로 보낸다.** 같은 워크트리·같은 맥락에서
  이어지고, 끝나면 다시 완료 알림이 온다.
- **격리는 Claude Code가 강제한다.** 구현자가 메인 체크아웃의 파일을 고치거나 그쪽으로 git을
  돌리면 도구가 막는다 — "이슈 브랜치에 커밋하지 않는다"가 규칙이 아니라 구조가 된다.
- **변경 없이 끝나면 워크트리와 브랜치가 자동 삭제된다.** 커밋이 있으면 남는다(8절에서 정리).

**사람이 별 세션으로 워크트리를 띄우지 않는 이유.** 별 세션도 동작하지만 정의 적용
(에이전트 지정 누락 시 일반 세션), 완료 신호(알림·훅 기록 없음), 의존성 설치 디렉터리 공유를
손으로 다뤄야 한다. `Agent` 툴은 이 셋을 기본으로 해결한다.

### 진행이 의심될 때

완료 알림이 오기 전에 확인하려면 워크트리의 커밋을 본다:

```bash
git -C .claude/worktrees/agent-<id> log --oneline <핸드오프커밋>..HEAD
```

## 5. 의존성 설치 디렉터리 — 워크트리마다 따로

Claude Code 워크트리는 gitignore된 의존성 설치 디렉터리(가상환경, `node_modules` 등)를 공유하지 않는다.
워크트리에서 처음 `check_cmd`가 돌 때 그 안에 새로 만든다(시간이 걸린다 — 정상이다).
그래서 **워크트리의 테스트는 그 워크트리의 코드를 검사한다** — 공유 설치 디렉터리가 메인의 옛
코드를 읽어 테스트가 엉뚱한 코드를 검사하는 사고가 구조적으로 생기지 않는다.

**의존성 추가는 여전히 사람이 한다.** 의존성 매니페스트·잠금 파일을 바꾸는 결정이다.
필요하면 최종 보고에 blocker(`owner: "human"`)로 적고 멈춘다.

> 사람이 다른 도구로 워크트리를 만들면서 설치 디렉터리를 공유(symlink)하게 했다면, 그 워크트리에서는
> 설치·동기화 명령도 다른 워크트리를 오염시키므로 실행하지 않는다.

## 6. 커밋

**`commit-msg` 훅이 강제한다** — 형식이 틀리면 커밋이 막힌다:

```
<타입> : <제목>      팀 전역 커밋 템플릿 형식
  feat · fix         기능 변경·버그 수정 — 꼬릿말 `Tests: T<n>[,T<m>]` 필수
  refact · style     동작 불변 정리·서식 — tests_dir 변경 금지
  docs               spec·계약 핸드오프 (오케스트레이터)
  test               계약 테스트 핸드오프 (오케스트레이터)
  chore              설정·도구·로컬 머지
```

**기능과 구조를 한 커밋에 섞지 않는다**(Tidy First). 섞이면 리뷰에서 "동작이 바뀐 것인가"를
판단할 수 없고, 되돌릴 때 함께 날아간다. 상세: `issue-harness:tdd-cycle`

- **작업 단위로 커밋한다.** 테스트 목록 항목 여러 개를 한 커밋에 묶을 수 있다
  (꼬릿말 `Tests: T1,T2`). 단 **오케스트레이터가 한 번에 보낸 단위(full은 모듈 묶음 하나, light는 묶음 전체)를 넘어서 묶지 않는다** —
  3c 검증과 되돌리기가 그 단위로 일어난다.
- **기존 테스트를 지우거나 바꾸면 꼬릿말로 선언한다** — `Test-Change: <대상> — <사유 또는 대체 ID>`.
  대상은 함수 이름, 클래스 메서드는 `Class.test_x`, 파일 전체는 `<경로>::*`. 선언이 없으면 `commit-msg` 훅이
  막고 대상 목록을 출력한다. 마커(데코레이터·`pytestmark`)를 붙이거나 떼는 것, 클래스 이름 변경, 함수를 다른 클래스로
  옮기거나 클래스로 감싸기, 파일 이름을 pytest 수집 규칙(`test_*.py`) 밖으로 바꾸기도 변경이다. 테스트 추가, `assert` 추가, assert 메시지 변경, parametrize 케이스 추가,
  같은 함수를 다른 파일로 옮기는 것은 선언하지 않는다. `--no-verify`는 쓰지 않는다.
- **항목 커밋은 관련 테스트(`test_file_cmd`) 통과 후, 묶음 보고는 `check_cmd` 통과 후.** 린터가 작업 트리를
  고치면 이후 `git diff`로 무엇이 바뀌었는지 본다. 통과 기준은 `issue-harness:tdd-cycle` 「묶음 끝 — `check_cmd` 한 번」.
- **이슈 브랜치에 커밋하지 않는다.** 구현자는 자신의 워크트리 브랜치에만 커밋한다.
  **오케스트레이터도 대칭으로 지킨다** — 워크트리가 도는 동안 이슈 브랜치에 커밋하지 않는다(8절 — 승인된 계약·spec 예외 포함).

## 7. 작업 완료 — 여기서 멈춘다

**구현자는 `git push`·PR 생성·머지를 하지 않는다.** 커밋까지 하고 멈춘다.

**로컬 머지(워크트리 → 이슈 브랜치)는 오케스트레이터가 한다.** origin을 건드리지 않아
되돌리기 쉽고(`git reset`), 머지해야 비로소 이슈 브랜치에서 상통합 검증을 할 수 있다.
push·PR은 확정된 PR 줄대로 한다 — `push 자동`이면 오케스트레이터가 묻지 않고, `push 사람`이거나 미확정이면
명령만 출력한다(8절). 기본 브랜치 머지는 항상 사람이다.

## 8. 워크트리 → 이슈 브랜치 반영 — 로컬 머지 경로

**워크트리 브랜치는 origin에 올리지 않는다.** 오케스트레이터가 이슈 브랜치에서 로컬 머지하고,
origin에는 이슈 브랜치만 올라간다. PR은 `이슈 브랜치 → 기본 브랜치` 하나뿐이다.

```
워크트리 브랜치  ──(로컬 머지)──▶  이슈 브랜치  ──(PR)──▶  기본 브랜치
   origin에 없음                    origin에 있음
```

### 규칙 — 이것을 어기면 분기가 난다

**1. 오케스트레이터는 워크트리 작업이 도는 동안 이슈 브랜치에 커밋하지 않는다.**
`.claude/`·`docs/` 기록도 마찬가지다. 머지 후에 몰아서 커밋한다.
(`.harness/`는 gitignore라 커밋 대상이 아니다 — primary에서 언제든 갱신한다.)

**예외 — 사람이 승인한 계약·spec 커밋.** 구현 중 계약이나 spec이 바뀌어 사람이 승인했으면 이슈 브랜치에 커밋하고
(바뀐 계약에 따른 계약 테스트 커밋 포함 — 제목·본문 짝은 `issue-harness:issue-harness` 「full — `3a-contract` → `3a-test`」의 커밋 형식대로, 기존 계약 테스트도 `issue-harness:verification-protocol` 「기존 계약 테스트 갱신」대로 찾아 고친다),
다음 go 직전에 오케스트레이터가 워크트리 브랜치로 머지한다(`issue-harness:issue-harness` 「go 직전 반영」).
이슈 브랜치 → 워크트리 한 방향이라 분기가 나지 않는다. 예외는 이것뿐이다 — 기록·문서는 여전히 머지 후에 커밋한다.

> 이것을 어기면 양방향 분기가 난다 — 양쪽에 각자 커밋이 쌓여 머지 때 충돌을
> 손으로 해소해야 한다.

**2. 구현자는 자기 워크트리 브랜치에만 커밋한다** (6절). 이슈 브랜치를 건드리지 않는다.

**3. `.harness/`는 gitignore되어 워크트리에 따라오지 않는다.** 훅도 `--git-common-dir`로
primary를 찾아 거기에만 쓴다(`issue-harness:harness-state`). 정본은 항상 primary 하나다.

### 로컬 머지 — 오케스트레이터가 실행한다

**머지 전 이슈 브랜치는 반드시 깨져 있다.** 계약 테스트는 이슈 브랜치에 커밋하고
구현은 워크트리에서 하므로, 머지 전에는 "새 값을 기대하는 테스트 + 옛 구현"이다.
**이 실패를 결함으로 읽지 마라.** 구조상 정상이고, 머지가 그것을 닫는다.

머지 조건 — **완료 알림·종료 기록만으로 머지하지 않는다.** "끝났다"만 뜻하고
"성공했다"가 아니다(`issue-harness:harness-state`). 넷을 확인한다(`<spec 커밋>`은 첫 spec 커밋 — `issue-harness:harness-state` 「진행 지점 복원」):

1. 워크트리에 기능 커밋이 있는가 (`git -C <워크트리> log <spec 커밋>..HEAD --grep "^Tests: T"` — 범위 없이 세면 다른 이슈 커밋이 섞인다)
2. `blockers`에 `resolved: false`가 없는가
3. `<spec 커밋>..HEAD`의 `Tests:` 꼬릿말 합집합이 테스트 목록 전체인가
4. `4c` — 워크트리 HEAD에서 `check_cmd`가 통과했는가

```bash
# 1. 이슈 브랜치에서 워크트리 브랜치를 머지
git switch <이슈브랜치>
git merge --no-ff <워크트리브랜치> -m "chore : 워크트리 브랜치를 이슈 브랜치에 반영한다 (#<번호>)"

# 2. 기본 브랜치가 앞서 있으면 반영한다 — 워크트리가 갈라진 뒤 머지된 다른 PR과의 충돌을 PR 전에 본다
git fetch origin <기본 브랜치>
git merge-base --is-ancestor origin/<기본 브랜치> HEAD || \
  git merge --no-ff origin/<기본 브랜치> -m "chore : <기본 브랜치>를 이슈 브랜치에 반영한다 (#<번호>)"

# 3. 상통합 검증 — 이슈 브랜치에 워크트리가 모르는 커밋이 있을 때만(2에서 반영했으면 해당한다).
#    머지 결과 트리가 워크트리 트리와 같으면 4c가 이미 같은 트리를 검사했다
[ "$(git rev-parse HEAD^{tree})" = "$(git rev-parse <워크트리브랜치>^{tree})" ] || <check_cmd>
```

**기본 브랜치 반영을 건너뛰지 않는다.** 다른 이슈가 먼저 머지되면 git 충돌 없이 결합이 깨진다 — 파일 이름만
다른 같은 마이그레이션 번호, 새로 들어온 테스트가 이번 이슈가 바꾼 권한·스키마에 기대는 경우. 4c는 갈라진 시점의
트리만 보므로 여기서만 드러난다. 충돌이 나면 해소한 뒤 `check_cmd`를 돌린다.

**커밋 메시지에 `merge:` 접두를 쓰지 마라** — `commit-msg` 훅이 거부한다. `chore :`로 쓴다.

`check_cmd`가 실패하면 **push하지 않고 고친다.** 워크트리가 갈라진 뒤 이슈 브랜치에 들어간 것과의 결합은
여기서만 드러난다.

### 사람이 실행할 명령 — PR 줄이 `push 사람`일 때

```
머지·검증 완료. 다음 명령을 실행하세요:

  git push -u origin <이슈브랜치>
  gh pr create --base <기본 브랜치> --title "<제목> (#<번호>)" --body-file <경로>
```

로컬 머지는 되돌릴 수 있지만 push는 외부로 나간다.

### 워크트리 정리 — 머지 후에 한다

**기본 브랜치 PR이 머지된 뒤에 지운다.** 그 전에 지우면 유일한 사본이 사라진다
(워크트리 브랜치는 origin에 없으므로 원격 백업이 없다).

```bash
git worktree list                                  # 미푸시 커밋·미머지 브랜치 확인
git worktree remove .claude/worktrees/agent-<id>   # 잠겨 있다고 거부하면 git worktree unlock 먼저
git branch -d worktree-agent-<id>                  # -d 로 한다. 미머지면 거부당하는 것이 안전장치다
```

Claude Code의 주기적 정리는 **커밋이 남은 워크트리를 지우지 않는다** — 직접 지운다.

**이슈 워크트리 안에 구현자 워크트리가 있으면 그것부터 지운다.** 이슈 워크트리를 먼저 지우면
안쪽 워크트리의 등록 정보와 `worktree-agent-*` 브랜치가 남는다. 놓쳤으면:

```bash
git worktree prune                  # 디렉터리가 사라진 워크트리 등록 정리
git branch -d worktree-agent-<id>   # 남은 구현자 브랜치
```

지우기 전 확인:
- 이슈 브랜치에 머지됐는가 (`git branch --merged <이슈브랜치>`에 나오는가)
- gitignore된 산출물(`_workspace/` 등) 중 보존할 것이 없는가
- 의존성 설치 디렉터리는 그 워크트리 전용 실체다 — 함께 지워져도 다른 곳에 영향이 없다

### 이미 워크트리 브랜치를 push한 경우

로컬 머지로 전환하면 **그 PR은 커밋 0건의 빈 PR이 된다.**

```bash
gh pr close <번호> --comment "로컬 머지 경로로 전환 — 이슈 브랜치에 직접 머지함"
git push origin --delete <워크트리브랜치>   # 기본 브랜치 PR 머지 후에 한다
```

## 테스트 시나리오

**정상 흐름:** 이슈 착수 → `issue-planner`가 spec 작성 → 계약 공백 발견하여
`contract-guardian`에게 확정 요청 → 핸드오프 커밋 → `Agent(isolation: worktree)`로
`implementer` 실행(모듈 묶음 1) → 완료 알림 → `integration-qa`가 경계면 검증 →
`SendMessage`로 다음 묶음 → … → 로컬 머지 → push 명령 출력하고 멈춤.

**에러 흐름:** 워크트리에서 `check_cmd`가 import 오류로 실패 → 원인이 외부 패키지
미설치 → 의존성 추가는 사람의 결정 → 구현자가 최종 보고에 blocker로 적고 멈춤.
