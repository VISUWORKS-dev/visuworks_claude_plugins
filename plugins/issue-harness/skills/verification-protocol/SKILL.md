# Verification Protocol — 2단계 검증과 계약 TDD

검증을 두 번 한다. **보는 것이 다르기 때문**이지 꼼꼼히 하려는 것이 아니다.

경로·명령은 `.claude/harness.config.json`의 값이다(`contract_skill`, `contract_tests_dir`,
`contract_test_cmd`, `src_dirs`, `tests_dir`, `spec_dir`). 오케스트레이터가 프롬프트에 담아 준다.

| 단계 | 보는 것 | 답하는 질문 | 못 보는 것 |
|---|---|---|---|
| **1. 무컨텍스트** | 코드·테스트·실제 산출물 | 이 코드가 **실제로 무엇을 하는가** | 이게 요구사항인지 |
| **2. 컨텍스트** | 1의 결과 + 계약·spec 문서·이슈 | **명세대로 만들었는가** | 명세 자체의 오류 |

**두 결과가 불일치하는 지점이 가장 값진 발견이다.** 명세와 구현이 갈라진 곳이기 때문이다.
불일치가 없으면 둘 다 맞거나, 둘 다 같은 것을 놓친 것이다.

## 왜 무컨텍스트가 먼저인가

명세를 먼저 읽으면 코드를 그 명세대로 보게 된다. "응답에 `items` 필드가 있어야 한다"를
읽은 뒤 코드를 보면, `item`(단수)을 보고도 맞다고 읽는다. **확증편향은 의지로 막을 수 없고
순서로만 막는다.**

그래서 1단계는 명세를 **받지 않은 상태에서** 코드가 실제로 무엇을 내보내는지 기록한다.
그 기록을 2단계에서 명세와 대조한다.

## 1단계 — 무컨텍스트 검증

**실행 모드: 서브 에이전트** (팀 외부. 팀 안에 있으면 대화로 명세가 새어 들어온다)

### 차단 대상

| 준다 | 차단한다 |
|---|---|
| `src_dirs` 코드 | 계약 정본(`contract_skill`) |
| `tests_dir` 전부 | `<spec_dir>/issue-<N>.md` |
| 실제 산출물 파일 | 이슈 본문 (`gh issue view` 금지) |
| 이슈 번호·제목 | `state.json`의 `contracts` |

**이슈 제목까지는 준다.** 완전 무지 상태면 관련 없는 것까지 보고한다. 방향만 알고
상세 명세는 모르는 상태가 목표다.

### 프롬프트 형태

```
이슈 #<N> "<제목>" 구현의 실제 동작을 기록한다.

너는 이 이슈의 명세·계약 문서·작업 계획을 받지 못한다. 요청하지도 마라.
`gh issue view`, <contract_skill>, spec 문서를 읽지 않는다.

코드와 테스트를 읽고, 가능하면 실제로 돌려서 아래를 기록한다:
- 각 모듈이 실제로 내보내는 것 — 필드명·타입·중첩·nullable
- 각 모듈이 실제로 기대하는 입력
- 빈 입력·None·실패 시 실제 동작
- 모듈 간 실제로 이어지는가 (생산자 출력 → 소비자 입력)

"맞다/틀리다"를 판정하지 마라. 명세가 없으므로 판정할 수 없다.
**무엇을 하는지만** 기록한다. 이상해 보이는 것은 "관찰"로 적고 결론은 내지 않는다.
```

산출물: `_workspace/verify_<N>_blind.md`

## 2단계 — 컨텍스트 검증

**실행 모드: 서브 에이전트** (1단계와 다른 인스턴스)

1단계 보고서 + 계약 문서 + spec 문서 + 이슈 본문을 **전부** 준다.

```
1단계 무컨텍스트 보고서(_workspace/verify_<N>_blind.md)를 읽는다.
이것은 명세를 모르는 검증자가 기록한 "코드의 실제 동작"이다.

이제 <contract_skill> 계약, spec 문서, 이슈 #<N>을 읽고 대조한다:
- 1단계가 기록한 실제 동작 vs 계약이 요구하는 것 — 어디가 다른가
- 계약에 있는데 1단계가 발견하지 못한 것 — 미구현인가, 1단계가 놓친 것인가
- 1단계가 기록했는데 계약에 없는 것 — 명세 누락인가, 불필요한 구현인가
- spec 문서의 완료 조건이 실제로 충족되는가

**마지막 두 항목이 핵심이다.** 명세와 구현이 갈라진 지점이고,
어느 쪽이 틀렸는지는 임의로 정하지 말고 근거와 함께 보고한다.
```

산출물: `_workspace/verify_<N>_spec.md`

## 계약 TDD

### 범위 — 형태만, 내용은 아니다

| TDD 한다 | TDD 안 한다 |
|---|---|
| 스키마 필드 — 이름·타입·필수 여부 | 생성된 문안·요약의 품질 |
| 빈 결과(0건) 처리 | 선별·추천이 "적절한가" |
| None·누락 필드 처리 | 결과물이 "읽을 만한가" |
| 단계 간 상태값 문자열 (쓰는 쪽 ↔ 읽는 쪽) | 화면 디자인의 미적 판단 |
| 산출물 경로 일치 | |
| 중복 입력 처리 | |

**비결정적 출력(LLM 등)은 내용을 assert할 수 없다.** 대신 형태를 건다 —
항목이 N개인가, 각 항목에 필수 필드가 있는가, 탈락 근거가 남는가. 이것만으로도 소비자가
읽다가 터지는 것은 전부 막힌다.

**마감과 충돌하지 않는다.** 계약 테스트는 어차피 써야 하는 것을 먼저 쓰는 것뿐이고,
`issue-harness:scope-guard`가 "절제하지 않는 것"으로 지정한 항목과 정확히 겹친다.

#### 외부 호출을 끈 경로의 구멍 — 꺼진 분기는 단위 테스트가 맡는다

계약 테스트는 보통 외부 호출(LLM·외부 API)을 끈 경로(`--dry-run`, 가짜 클라이언트)로 돈다.
그러면 **외부 호출이 실행되는 분기는 검사하지 않는다.** 다음은 계약 테스트로 **막을 수 없다**:

- 외부 호출 결과가 만드는 상태 전이 (예: 응답에 따라 항목을 제외로 뒤집는 것)
- 그 전이와 다른 로직의 **호출 순서** 의존
- 외부 호출 실패·타임아웃 경로

계약 테스트 전건 통과가 이 경로의 정당성을 뜻하지 않는다. **꺼진 경로에서 실행되지 않는
분기에 걸리는 제약은 `implementer`가 단위 테스트로 직접 쓴다** — 결과 객체를 직접 보거나
외부 호출을 가짜로 세운다.

**확인법: 고의 변형(mutation).** 막고자 하는 제약을 **일부러 깨뜨려** 돌려 본다.
계약 테스트가 전부 통과하면 그 제약은 무방비다. 통과하는 것을 확인하고 넘기지 말고,
**깨뜨렸을 때 실패하는지** 확인한다.

`4a`·`4b`도 꺼진 경로의 산출물만 보면 같은 구멍을 물려받는다.
**완료 조건이 외부 호출 경로의 산출물을 판정 기준으로 지정했다면 꺼진 경로 결과로 충족을
주장할 수 없다** — 실호출로 한 번 만들어 수치를 기록한다.

### 순서

```
3a 계약 확정 (contract-guardian)
   ↓
3a-test  integration-qa가 실패 테스트를 쓴다 → <contract_tests_dir>
   ↓     (반드시 실패하는 것을 확인하고 넘긴다)
3b 구현  implementer가 통과시킨다
   ↓
3c 점진 검증
```

**QA가 먼저 쓰는 이유:** 구현자가 테스트를 쓰면 자기 설계에 맞춘 테스트가 된다.
구현이 틀려도 테스트가 같이 틀려서 통과한다. 계약을 소유하지 않고 구현도 하지 않는
제3자가 쓸 때만 테스트가 독립적인 판정 기준이 된다.

### 디렉터리 소유권

| 경로 | 쓰는 주체 | 내용 |
|---|---|---|
| `contract_tests_dir` | **`integration-qa`** | 계약·경계면 테스트 |
| `tests_dir` 나머지 | `implementer` | 단위 테스트 |
| `src_dirs` | `implementer` | 제품 코드 |

`integration-qa`는 `contract_tests_dir`와 `_workspace/`만 쓴다. **제품 코드는 여전히 금지** —
검증자가 제품 코드를 고치면 자기 구현을 자기가 검증하는 구조가 된다.
`implementer`는 `contract_tests_dir`를 **고치지 않는다.** 통과시키지 못하면 구현을 고치거나,
계약이 틀렸다고 판단되면 `contract-guardian`에게 판단을 요청한다.

### 실패 확인 의무

테스트를 쓴 뒤 **반드시 실패하는 것을 확인하고 넘긴다.**

```bash
<contract_test_cmd>   # 이 시점에 실패해야 한다
```

통과하면 둘 중 하나다 — 이미 구현되었거나, 테스트가 아무것도 검증하지 않거나.
후자가 훨씬 흔하다. 실패를 확인하지 않은 테스트는 나중에 통과해도 의미가 없다.

## state.json 기록

```jsonc
"verification": {
  "blind":    { "status": "done", "output": "_workspace/verify_12_blind.md" },
  "spec":     { "status": "done", "output": "_workspace/verify_12_spec.md" },
  "mismatches": 2,        // 1단계와 2단계가 갈라진 지점 수
  "contract_tests": { "written": 7, "failing_at_write": 7, "passing_now": 5 }
}
```

`failing_at_write`가 `written`보다 작으면 **빈 테스트를 쓴 것이다.** 오케스트레이터는 이 경우
다음 단계로 보내지 않는다.

## 에러 핸들링

| 상황 | 전략 |
|---|---|
| 1단계가 명세를 요청 | 주지 않는다. 명세 없이 가능한 범위만 기록하게 한다 |
| 1단계가 코드를 못 돌림 | 실행 대신 샘플 기반으로 기록하고 "실행 미검증"으로 명시 |
| 1·2단계 불일치 발생 | 어느 쪽이 맞는지 임의 판정 금지. 근거와 함께 사람에게 보고 |
| 계약 테스트가 처음부터 통과 | 테스트가 비었다고 보고 다시 쓴다 |
| 계약 테스트를 통과 못 시킴 | 테스트를 고치지 않는다. 구현을 고치거나 `contract-guardian`에게 계약 판단 요청 |

## 테스트 시나리오

**정상:** 구현 완료 → 1단계가 "응답에 `item` 단수 필드, 각 항목에 `id`/`name`/`url`"로
기록 → 2단계가 계약의 `items`(복수)와 대조해 불일치 1건 발견 → 어느 쪽이 정본인지
`contract-guardian`에게 판단 요청 → 계약이 맞다고 판정 → `implementer`가 구현 수정.

**에러:** 계약 테스트 7개를 썼는데 작성 시점에 3개가 통과 → 그 3개는 아무것도 검증하지
않는 테스트 → `integration-qa`가 다시 쓰고, 오케스트레이터는 `3b`로 보내지 않는다.
