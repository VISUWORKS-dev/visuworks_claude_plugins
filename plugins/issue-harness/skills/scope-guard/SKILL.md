# Scope Guard — 지금 필요한 것만 만든다

마감이 있는 작업에서 가장 흔한 실패는 기능 부족이 아니라 **범위 초과로 아무것도 완성되지 않는 것**이다.

프로젝트 고유의 판정 사례(범위 밖으로 확정된 기능, 이미 다른 레포가 책임지는 것)가 있으면
`.claude/harness.config.json`의 `domain_skills.scope`가 가리키는 스킬에 있다. 함께 읽는다.

## 판정 질문 — 순서대로 묻는다

첫 질문에서 걸리면 거기서 멈춘다.

**1. 이번 이슈의 완료 조건이 이걸 요구하는가?**
아니면 만들지 않는다. "만들어두면 나중에 편하다"는 이번 이슈 이후의 이야기다.

**2. 이게 없으면 결과물이 멈추는가?**
멈추지 않으면 우선순위를 내린다. 멈추게 하는 것부터 만든다.

**3. 이미 있는 것으로 되는가?**
표준 라이브러리, 이미 설치된 의존성, 이 저장소에 이미 있는 코드, 다른 레포가 책임지는 기능.
다른 레포의 책임을 이 저장소에 다시 구현하지 않는다 — 호출한다.

**4. 한 줄로 되는가?**
되면 한 줄로 한다.

**5. 최소 코드는 무엇인가?**
여기까지 왔으면 만든다. 최소로.

## 만들지 않는 것

| 항목 | 이유 |
|---|---|
| 구현이 하나뿐인 인터페이스·추상 클래스 | 두 번째 구현이 생길 때 만든다 |
| 값이 변하지 않는 것의 설정화 | 변할 때 설정으로 뺀다 |
| 이슈 본문이 범위 밖으로 명시한 기능 | 명시적 제외를 구현하면 리뷰에서 되돌린다 |
| 다른 레포가 책임지는 로직 자체 | 수정이 필요하면 그 레포에 이슈를 올리고 링크만 남긴다 |
| 나중을 위한 스캐폴딩 | 나중이 스스로 만든다 |
| 결과물에 쓰이지 않는 스키마 필드 | 계약에 들어간 필드는 모든 생산자·소비자가 구현해야 한다 |

## 절제하지 않는 것

아래는 마감이 있어도 줄이지 않는다. 줄이면 결과물이 쓰이는 자리에서 터진다.

- **빈 결과와 실패의 구분** — 0건은 정상, 실패는 에러. 같게 처리하면 "왜 아무것도 안 나오지"의
  원인을 못 찾는다.
- **경계면 계약 준수** — 계약을 어기고 빨리 만든 모듈은 연결 단계에서 시간을 두 배로 쓴다.
- **산출물 형식의 실제 제약** — 결과물이 소비되는 환경(메일 클라이언트, 외부 시스템 입력 형식 등)의
  제약. 개발 환경에서 보기 좋은 형식으로 만들면 실제 환경에서 깨진다.
- **`check_cmd` 통과** — CI가 이걸 돌린다. 깨진 채로 넘기면 다음 사람이 고친다.
- **최소 한 개의 검증** — 비어있는 테스트나 skip은 통과가 아니다.

## 범위 초과의 조짐

아래가 보이면 멈추고 판정 질문으로 돌아간다:

- "일반화해두면" / "확장 가능하게" / "나중에 바꾸기 쉽게"
- 완료 조건에 없는 화면·엔드포인트·CLI 옵션을 만들고 있다
- 계획(spec 문서)에 없는 파일을 만들고 있다
- 테스트를 위해 제품 코드에 훅을 넣고 있다

## 범위를 자를 때의 기록

잘라낸 것은 **지우지 않고 남긴다.** 두 곳 중 하나에:

- spec 문서의 `## 범위 밖` 절
- 코드 주석: `# ponytail: <잘라낸 것>, <필요해지는 조건>일 때 추가`

기록 없이 자르면 나중에 "이거 왜 없지"를 다시 판단해야 한다.

## 판정 예시

| 상황 | 판정 |
|---|---|
| "입력 소스를 나중에 추가하기 쉽게 플러그인 구조로" | **만들지 않음.** 질문 1에서 탈락. 지금 소스 목록은 고정이다 |
| "외부 API 호출 실패 시 재시도" | **만든다.** 질문 2 통과 — 실패하면 결과물이 멈춘다 |
| "중간 결과를 DB에 저장" | **만들지 않음.** 파일로 된다(질문 3). 전달 방식을 정하는 이슈에서 재검토 |
| "내부용 화면에 로그인" | **만들지 않음.** 이슈가 단일 사용자 전제를 명시했다면 범위 밖 |
| "입력 0건일 때 처리" | **만든다.** 절제하지 않는 항목 |
