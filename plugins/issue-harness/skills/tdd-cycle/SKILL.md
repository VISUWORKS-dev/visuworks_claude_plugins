# TDD 사이클 — 한 번에 항목 하나

spec 문서의 `## 테스트 목록`에서 **항목 하나**를 골라 아래 순서로 통과시킨다. 두 항목을 같이 하지 않는다.

오케스트레이터는 **모듈 묶음**(`### M1` 아래 항목들) 단위로 "go"를 보낸다. 받은 묶음만 하고 보고하고 멈춘다.
light 경로는 한 번의 "go"에 묶음 전체가 온다 — 그래도 묶음마다 아래 「묶음 끝」을 거친다.

`check_cmd`·`test_file_cmd`·`tests_dir`·`contract_tests_dir`는 프롬프트의 `[프로젝트 값]`이다.

**하네스 안에서는 이 스킬이 정본이다.** 다른 TDD 스킬(예: `mattpocock-skills:tdd`)이 함께 설치돼 있어도 로드하지 않는다.
테스트 경계(무엇을 어디까지 테스트할지)는 `2b`에서 승인된 테스트 목록이 이미 정했다 — 사람에게 다시 묻지 않는다.
백그라운드에서 돌기 때문에 물으면 답이 오지 않고 멈춘다.

## 사이클 — 항목마다

1. **실패 테스트를 쓴다.** 항목의 기대값을 그대로 단정문으로 옮긴다. 항목에 적힌 테스트 파일(모듈 기준)에 쓴다.
   등급 규칙을 따른다: `화면`은 200과 핵심 데이터만(class 이름·문구·태그 개수 단정 금지), `로직`은 parametrize 표 하나.
2. **실패를 확인한다.** 여기서 통과하면 그 테스트는 아무것도 검증하지 않는다 — 다시 쓴다.
   **예외 — 앞 항목 구현으로 이미 통과.** 단정의 기대값을 잠시 틀린 값으로 바꿔 실패하는지 본다. 실패하면 테스트는
   맞다 — 되돌리고 구현 없이 `test : <제목>` + `Tests: T<n>`으로 커밋하고, 보고 `evidence`에 「선통과 — T<m> 구현으로」를 적는다.
   바꿔도 통과하면 단정이 비어 있다 — 다시 쓴다.
3. **최소 구현.** 다음 항목을 미리 만들지 않는다.
4. **관련 테스트만 돌린다.** `test_file_cmd`에 이 묶음의 테스트 파일(항목에 적힌 파일 + 묶음이 소비하는
   `contract_tests_dir` 파일)을 넣는다. 묶음 안의 앞 항목을 깨뜨렸으면 멈추고 고친다.
   `test_file_cmd`가 없으면 `check_cmd`를 돌린다.
5. **필요하면 구조 정리.** 중복이 눈에 보일 때만.

## 묶음 끝 — `check_cmd` 한 번

묶음의 마지막 항목을 통과시킨 뒤 **`check_cmd`를 한 번** 돌린다(lint·typecheck·전체 테스트).
아래 통과 기준을 만족할 때까지 고치고 다시 돌린다. 그 출력이 보고의 `evidence`다.

**통과 기준 — 뒤 묶음 계약 테스트의 구현 없음 실패는 남겨도 된다 (full).** `3a-test`가 모든 묶음의 계약 테스트를
먼저 커밋하므로, 앞 묶음 시점에는 뒤 묶음 계약 테스트가 실패한다. 실패한 테스트가 **모두** 아래 둘을 만족하면 통과다
(`result: pass`).

- `3a-test` 커밋 본문에서 이번 묶음보다 뒤 묶음의 항목(`T<n>`)에 짝지어진 계약 테스트다. 본문은 다음으로 읽는다.
  `git log --grep "^test : 이슈 #<N> 계약 테스트" --format=%b` — 같은 테스트가 여러 번 나오면 먼저 나온(최신) 줄이 짝이다
- 실패 원인이 구현 없음이다(뒤 묶음 제품 모듈이 없어 난 import 오류 포함) — 판정은 `issue-harness:verification-protocol` 「실패 확인 의무」

그 밖의 실패는 고친다 — 짝이 없거나 이번·앞 묶음에 짝지어진 계약 테스트, 단위 테스트, lint·typecheck, 구현 없음이 아닌 원인.
`check_cmd`가 테스트 실패에서 멈춰 뒤 단계(lint 등)가 돌지 않았거나, 수집 오류로 테스트 실행이 중단됐으면
짝이 모두 뒤 묶음인 파일만 빼고 나머지를 따로 돌려 통과를 확인하고 그 명령과 실행 수를 `evidence`에 적는다.
수집 오류를 낸 파일에 이번·앞 묶음 짝이 섞여 있으면 빼지 않는다 — 테스트 결함이므로 `blockers:`로 보고한다.
남긴 실패는 `evidence`에 테스트마다 한 줄로 적는다 — `3c`가 직접 다시 판정하고 이 목록과 대조한다.

```
뒤 묶음 실패: <테스트 이름> — T<n>, 구현 없음 (<실패 출력 한 줄>)
```

항목마다 `check_cmd`를 돌리지 않는다 — 전체 테스트가 수 분이면 항목 수만큼 곱해진다. 다른 모듈을
깨뜨린 것은 여기서 잡힌다.

## 커밋 — 기능과 구조를 섞지 않는다

| 커밋 | 언제 | 형식 |
|---|---|---|
| 기능 | 항목을 통과시켰을 때 | `feat : <제목>` + 꼬릿말 `Tests: T<n>[,T<m>]` (버그면 `fix`) |
| 구조 | 동작을 바꾸지 않고 정리했을 때 | `refact : <제목>` (서식만이면 `style`) |

- 한 커밋에 섞지 않는다(Tidy First). 구조 정리를 먼저 하고 기능을 얹는다.
- 같은 묶음 안의 항목은 한 커밋에 묶을 수 있다(`Tests: T1,T2`). **묶음을 넘어서 묶지 않는다.**
- 항목 커밋은 관련 테스트 통과 후 해도 된다. 묶음 끝 `check_cmd`가 lint 등으로 실패해 고친 것은
  별도 커밋(`style`·`fix`)으로 올린다. **보고는 `check_cmd`가 「묶음 끝 — `check_cmd` 한 번」 통과 기준을 만족한 뒤에만** 한다.
- `refact`·`style` 커밋은 `tests_dir`를 건드릴 수 없다 — git hook이 막는다.

## 하지 않는 것

- **목록에 없는 기능을 만들지 않는다.** 필요해 보이면 `questions:`에 적는다.
- **목록의 기대값을 바꾸지 않는다.** 틀렸다고 판단되면 구현을 멈추고 `questions:`로 보고한다.
- **계약 테스트(`contract_tests_dir`)를 고치지 않는다.** 계약이 틀렸다고 판단되면 보고로 `contract-guardian` 판단을 요청한다.
- **동어반복 테스트를 쓰지 않는다.** 구현과 같은 식으로 기대값을 계산하는 단정(`assert f(x) == x * 2`인데 `f`가 `x * 2`)은 구현이 틀려도 통과한다. 기대값은 목록에 적힌 값을 그대로 쓴다.
- **내부 협력자를 mock하지 않는다.** 이 저장소 안의 모듈은 실제로 호출한다. 가짜로 세우는 것은 외부 경계(외부 API·LLM·시간·네트워크)뿐이다.
- **같은 항목에서 3회 실패하면 멈춘다.** `result: blocked`로 보고하고 시도한 것과 안 된 이유를 적는다.

## 최종 보고

```
item: M1 (T1,T2,T3)
result: pass | fail | blocked
evidence: <check_cmd> 실제 출력 요약, 커밋 해시, 뒤 묶음 실패 목록(있을 때만)
questions: (있을 때만)
next: (fail일 때)
```
