# TDD 사이클 — 한 번에 항목 하나

spec 문서의 `## 테스트 목록`에서 **항목 하나**를 골라 아래 순서로 통과시킨다. 두 항목을 같이 하지 않는다.

오케스트레이터는 **모듈 묶음**(`### M1` 아래 항목들) 단위로 "go"를 보낸다. 받은 묶음만 하고 보고하고 멈춘다.
light 경로는 한 번의 "go"에 묶음 전체가 온다 — 그래도 묶음마다 아래 「묶음 끝」을 거친다.

`check_cmd`·`test_file_cmd`·`tests_dir`·`contract_tests_dir`는 프롬프트의 `[프로젝트 값]`이다.

## 사이클 — 항목마다

1. **실패 테스트를 쓴다.** 항목의 기대값을 그대로 단정문으로 옮긴다. 항목에 적힌 테스트 파일(모듈 기준)에 쓴다.
   등급 규칙을 따른다: `화면`은 200과 핵심 데이터만(class 이름·문구·태그 개수 단정 금지), `로직`은 parametrize 표 하나.
2. **실패를 확인한다.** 여기서 통과하면 그 테스트는 아무것도 검증하지 않는다 — 다시 쓴다.
3. **최소 구현.** 다음 항목을 미리 만들지 않는다.
4. **관련 테스트만 돌린다.** `test_file_cmd`에 이 묶음의 테스트 파일(항목에 적힌 파일 + 묶음이 소비하는
   `contract_tests_dir` 파일)을 넣는다. 묶음 안의 앞 항목을 깨뜨렸으면 멈추고 고친다.
   `test_file_cmd`가 없으면 `check_cmd`를 돌린다.
5. **필요하면 구조 정리.** 중복이 눈에 보일 때만.

## 묶음 끝 — `check_cmd` 한 번

묶음의 마지막 항목을 통과시킨 뒤 **`check_cmd`를 한 번** 돌린다(lint·typecheck·전체 테스트).
실패하면 고치고 다시 돌린다. 통과한 출력이 보고의 `evidence`다.

항목마다 `check_cmd`를 돌리지 않는다 — 전체 테스트가 수 분이면 항목 수만큼 곱해진다. 다른 모듈을
깨뜨린 것은 여기서 잡힌다.

## 커밋 — 기능과 구조를 섞지 않는다

| 커밋 | 언제 | 형식 |
|---|---|---|
| 기능 | 항목을 통과시켰을 때 | `feat : <제목>` + 꼬릿말 `Tests: T<n>[,T<m>]` (버그면 `fix`) |
| 구조 | 동작을 바꾸지 않고 정리했을 때 | `refact : <제목>` (서식만이면 `style`) |

- 한 커밋에 섞지 않는다(Tidy First). 구조 정리를 먼저 하고 기능을 얹는다.
- 같은 묶음 안의 항목은 한 커밋에 묶을 수 있다(`Tests: T1,T2`). **묶음을 넘어서 묶지 않는다.**
- 항목 커밋은 관련 테스트 통과 후 해도 된다. 묶음 끝 `check_cmd`가 lint 등으로 실패해 고친 것은
  별도 커밋(`style`·`fix`)으로 올린다. **보고는 `check_cmd` 통과 뒤에만** 한다.
- `refact`·`style` 커밋은 `tests_dir`를 건드릴 수 없다 — git hook이 막는다.

## 하지 않는 것

- **목록에 없는 기능을 만들지 않는다.** 필요해 보이면 `questions:`에 적는다.
- **목록의 기대값을 바꾸지 않는다.** 틀렸다고 판단되면 구현을 멈추고 `questions:`로 보고한다.
- **계약 테스트(`contract_tests_dir`)를 고치지 않는다.** 계약이 틀렸다고 판단되면 보고로 `contract-guardian` 판단을 요청한다.
- **같은 항목에서 3회 실패하면 멈춘다.** `result: blocked`로 보고하고 시도한 것과 안 된 이유를 적는다.

## 최종 보고

```
item: M1 (T1,T2,T3)
result: pass | fail | blocked
evidence: <check_cmd> 실제 출력 요약, 커밋 해시
questions: (있을 때만)
next: (fail일 때)
```
