# Weekly Report (업무 DB → 연구노트 금주/차주 진행 사항)

> **역할 분담**: 이 스킬은 Notion 안에서만 동작한다 — 업무 DB에서 이번 주·다음 주
> 내 업무를 모아 연구노트의 금주/차주 진행 사항·이슈사항·공유사항을 채운다. vault
> 기록은 obsidian-vault-manager, 회의록·공용 문서는 visuworks-work-manager 담당이다.

## 0. 질문 방식

- 사용자에게 묻는 모든 항목(완료 여부, 차주 편입 여부, 섹션별 추가 작성 등)은
  **가능하면 줄글 질문이 아니라 AskUserQuestion으로 항목별로** 묻는다. 자유
  서술이 꼭 필요한 경우(미완료 사유, 진행 요약, 추가 작성 내용 등)만 텍스트로
  받는다.

## 1. 설정값과 캐시

이 스킬은 두 종류의 값을 다룬다. **매 실행 확인**과 **최초 1회 확인**을 섞지 않는다.

- **userConfig(설치 시 입력, 있으면 최우선 사용)**
  - `weekly_report_work_db_url` — 업무 DB(예: `2026 업무 DB`) URL
  - `weekly_report_notes_db_url` — 연구노트(주간 업무 보고) DB URL
  - `weekly_report_my_name` — 업무 DB 작업자 필드에서 본인을 찾을 Notion 표시 이름
- **캐시(`.omc/state/weekly-report.json`, 이 스킬이 최초 확인 후 직접 기록)**
  - `work_db_url`, `notes_db_url` — userConfig에 없어 사용자에게 물어 확정한 경우 여기 저장
  - `my_mention` — 업무 DB `작업자` person 필드에서 확정된 본인의 mention (url/id, 표시 이름)
  - 캐시 파일이 있으면 그 값을 그대로 쓰고 사용자에게 다시 묻지 않는다.

우선순위: **캐시 → userConfig → 사용자에게 질문(최초 1회, 확인 즉시 캐시에 기록)**.
DB URL이 바뀌었거나 계정 정보가 잘못됐다고 사용자가 말하면 그때만 캐시를 갱신한다.

## 2. 최초 설정 (Setup — 캐시가 없을 때만 실행)

캐시 파일(`.omc/state/weekly-report.json`)이 없거나 필요한 키가 비어 있을 때만
아래를 수행한다. 캐시가 이미 채워져 있으면 이 절 전체를 건너뛰고 바로 3절로 간다.

### ① DB URL 확보

- `work_db_url`, `notes_db_url` 각각: 캐시 → userConfig → 없으면 사용자에게
  Notion URL을 요청한다. 다른 DB를 추측해서 찾지 않는다.
- 두 URL을 확보하면 fetch해서 실제로 존재하고 접근 가능한지 확인한다.
- 업무 DB: `이름`(제목), `작업자`(person), `Sprint`(multi_select, `YYYY-M-주차`
  형식), `시작날짜`/`종료날짜`, 프로젝트 relation이 있어야 한다. **완료 여부
  속성은 없다** — 완료 판단은 매 실행마다 항상 사용자에게 묻는다(캐시 대상 아님).
- 보고 DB: 주차별 페이지(`YY-MM-WW주차 연구노트`) 안에 업무 DB를 inline embed한
  표 + `금주 진행 사항`/`차주 진행 사항`/`이슈사항`/`공유사항` toggle 구조를
  기대한다. 구조가 다르면 사용자에게 알리고 어디에 쓸지 확인한다.
- 보고 DB에 페이지 템플릿(예: `YY-MM-WW주차 연구노트`)이 있으면 그 템플릿 URL도
  같이 기록해 둔다 — 새 주차 페이지를 만들 때 사용한다(6절 참고).

### ② 본인 식별

- `notion-fetch id="self"`가 돌려주는 Notion 계정 ID는 **업무 DB person 필드의
  mention ID와 다를 수 있다** (같은 사람이어도 값이 불일치하는 경우가 실측
  확인됨). self ID를 그대로 "나"로 간주해 필터링하지 않는다.
- `weekly_report_my_name`(userConfig)이 있으면 그 이름을 쓰고, 없으면 사용자에게
  본인 표시 이름을 묻는다.
- 업무 DB를 조회해 등장하는 작업자 mention들을 확인하고, 그 표시 이름들 중
  확보한 이름과 일치하는 mention을 찾아 "나"로 확정한다.
- 이름만으로 특정이 안 되면(동명이인, 표시 이름 불일치 등) 사용자에게 직접 물어
  확정한다 — mention ID를 임의로 추가 조회하거나 추측해서 확정하지 않는다.

### ③ 캐시 기록

- ①②에서 확정된 `work_db_url`, `notes_db_url`, `template_url`(있으면),
  `my_mention`(mention url/id + 표시 이름)을 `.omc/state/weekly-report.json`에
  저장한다.
- 저장 후 "다음부터는 다시 묻지 않는다"는 것을 사용자에게 한 줄로 알린다.

## 3. Sprint 값 계산 및 업무 조회

- Sprint는 `YYYY-M-주차` 형식이다. 오늘 날짜 기준으로 이번 주 값과 다음 주 값을
  둘 다 계산한다.
- 업무 DB의 Sprint 옵션 목록에 계산값이 없으면(신규 주차라 옵션이 아직 없는 경우)
  **추측해서 만든 값을 그대로 쓰지 말고** 사용자에게 "이번/다음 주 Sprint 값이
  `{계산값}`인데 DB 옵션에 없습니다, 맞나요?"라고 확인한다.
- 업무 DB에서 `작업자 = 캐시의 my_mention`인 내 업무 전체를 가져온다(뷰에 필터가
  안 걸려 있으면 조회 결과를 받은 뒤 직접 걸러낸다 — 뷰의 필터 유무를 신뢰하지
  않는다). 가져온 뒤 다음 세 그룹으로 나눈다.
  1. **금주 그룹** — Sprint에 이번 주 값이 포함된 업무
  2. **차주 확정 그룹** — Sprint에 다음 주 값이 포함된 업무 (이미 확정됨)
  3. **Sprint 미정 그룹** — 내 업무이지만 Sprint에 이번 주/다음 주 값이 둘 다
     없는 업무 (다른 과거·미래 주차 값만 있거나 Sprint 자체가 비어 있는 경우)
- 세 그룹 모두 0건이면 그대로 사용자에게 알리고 멈춘다 — 없는 업무를 지어내지 않는다.

## 4. 금주 그룹 처리

### ① 완료 여부 확인

- 금주 그룹 각 항목에 대해 AskUserQuestion으로 완료/진행중/미완료 여부를 묻는다.
- **미완료로 답한 항목은 반드시 이유를 함께 묻는다** (막힌 이슈, 우선순위 변경,
  외부 의존 대기 등 — 자유 서술). 이유 없이 "미완료"로만 기록하지 않는다.
- 완료·진행중으로 답한 항목도 한 줄 진행 요약(무엇을 했는지, 자유 서술)을 받는다
  — 업무 DB 항목 제목만으로 진행 사항을 지어내지 않는다.

### ② 산출물 링크 확인

- 각 업무 페이지를 fetch해 `Git Issue :` / `Git PR :` 같은 링크 라인이 비어 있는지
  확인한다.
- 비어 있고 사용자가 이번 대화에서 관련 GitHub PR/이슈, Figma 링크 등을 언급했거나
  가지고 있다면 채울지 AskUserQuestion으로 묻는다. **URL을 추측하거나 검색해서
  채우지 않는다** — 사용자가 준 링크만 쓴다.
- 이미 채워진 링크는 그대로 두고 중복 기재하지 않는다.

## 5. 차주 그룹 처리

- **차주 확정 그룹**은 그대로 차주 진행 사항 후보에 포함한다(사용자 확인 불필요 —
  Sprint가 이미 다음 주로 확정돼 있으므로).
- **Sprint 미정 그룹**은 업무 목록을 보여주고, 어떤 업무를 차주로 편입할지
  AskUserQuestion(다중 선택)으로 고르게 한다. 아무것도 고르지 않으면 이번 실행의
  차주 진행 사항에서 제외한다(업무 DB 자체는 건드리지 않는다).
- 사용자가 편입을 선택한 업무는:
  1. 해당 업무의 `Sprint` 속성에 다음 주 값을 추가하도록 업데이트할지 확인받고
     승인되면 업무 DB 페이지를 갱신한다.
  2. 담당자(작업자)가 바뀌는 경우가 있으므로, 편입한 업무마다 "담당자를 그대로
     유지할지, 바꿀지"를 AskUserQuestion으로 묻는다. 바꾼다고 답하면 새 담당자
     표시 이름을 받아 업무 DB person 필드를 갱신한다 — mention을 추측해서
     채우지 않고, 이름으로 확정이 안 되면 사용자에게 다시 확인한다.
- 차주 진행 사항에 들어갈 각 업무도 금주와 동일하게 한 줄 계획 요약(자유 서술)을
  받는다 — 제목만으로 계획을 지어내지 않는다.

## 6. 프로젝트별 그룹핑 및 Multi-select

- 금주·차주에 포함된 모든 업무를 업무 DB의 프로젝트/프로덕트 relation 기준으로
  프로젝트별로 묶는다. 작성 시 각 프로젝트 그룹 상단에 `[프로젝트명]` 헤더를
  붙인다 (예: `[DataPlatform]`).
- relation이 없는 업무는 `[미분류]`로 묶는다.
- 연구노트 페이지의 `Multi-select` 속성을, 이번 실행에서 등장한 프로젝트 이름들에
  맞춰 업데이트한다(기존 옵션 중 일치하는 것을 선택). DB Multi-select 옵션에
  없는 새 프로젝트명이면 새 옵션을 만들지, 사용자에게 먼저 확인한다.

## 7. 이슈사항 / 공유사항

- 이슈사항과 공유사항은 **한 번에 같이** AskUserQuestion으로 묻는다 — "이번 주
  이슈사항이나 공유사항으로 추가할 내용이 있나요?" 질문에 옵션은 정확히
  **"없음" / "직접 입력"** 두 개만 제공한다.
- "없음"이면 해당 섹션은 비워 두거나 기존 내용을 유지하고, 없는 내용을 지어내지
  않는다.
- "직접 입력"이면 이어서 자유 서술로 내용을 받는다(AskUserQuestion의 Other 응답을
  그대로 써도 되고, 바로 다음 턴에 텍스트로 받아도 된다).

## 8. 섹션별 추가 작성 확인

- 금주/차주 진행 사항 각각에 대해서도, 정리한 목록 외에 사용자가 추가로 적고 싶은
  내용이 있는지 AskUserQuestion으로 확인한다(업무 DB에 없는 항목을 자유롭게
  추가하고 싶을 수 있으므로). 옵션은 이슈/공유사항과 동일하게 **"없음" / "직접
  입력"** 두 개만 제공한다.
- "직접 입력"을 고르면 자유 서술로 추가 내용을 받는다.
- 추가된 내용은 해당 섹션의 업무 목록 뒤에 별도 항목으로 덧붙인다.

## 9. 확정 전 사용자 확인 (승인 게이트)

- 4~8절로 정리한 금주/차주 진행 사항(프로젝트별 그룹 포함)·미완료 사유·링크·
  이슈사항·공유사항 전체를 **표 또는 목록 형태로 요약해 보여주고**, "이대로
  연구노트에 작성해도 될지" 확인받는다.
- 사용자가 특정 항목의 내용이 사실과 다르다고 하면 그 항목만 다시 묻고 수정한다 —
  전체를 다시 만들지 않는다.
- 승인 전에는 Notion에 쓰지 않는다(차주 편입에 따른 업무 DB Sprint/담당자
  갱신도 포함해서, 승인 전에는 실행하지 않는다).

## 10. 작성

- 이번 주 연구노트 페이지가 있으면 그 페이지를 갱신한다.
- 없으면 **템플릿을 이용해 새로 생성**한다 — 캐시에 `template_url`이 있으면
  그 템플릿으로, 없으면 보고 DB의 기존 페이지 템플릿을 fetch해 구조(토글 섹션
  구성)를 확인한 뒤 동일한 구조로 새 페이지를 만든다. 임의로 다른 구조를
  지어내지 않는다. 새 페이지 생성 자체도 9절 승인에 포함한다.
- `금주 진행 사항` toggle 아래에 프로젝트별로 `[프로젝트명]` 헤더 + 업무별 항목
  (업무명 - 진행 내용/미완료 사유 - 링크)을 작성한다.
- `차주 진행 사항` toggle 아래에 동일한 방식으로 차주 업무를 작성한다.
- `이슈사항`/`공유사항` toggle에 7절 내용을 작성한다.
- 연구노트 페이지의 `Multi-select` 속성을 6절 기준으로 갱신한다.
- 차주 편입이 승인된 업무는 업무 DB 페이지의 `Sprint`(+ 필요 시 담당자)를 갱신한다.
- 업무 페이지의 산출물 링크 갱신이 승인됐다면 해당 업무 페이지도 함께 갱신한다.
- 쓰기 전 대상 페이지를 다시 fetch해 그 사이 내용이 바뀌지 않았는지 확인하고,
  기존 내용과 겹치면 새로 추가하지 말고 갱신한다.

## 11. 접근 범위 규율

- `notion-search`/워크스페이스 전체 쿼리를 자동으로 하지 않는다. 필요하면 인가를
  요청하고 승인 후에만 실행한다.
- 업무 DB·보고 DB 및 그 하위 페이지 외의 다른 Notion 콘텐츠는 사용자가 명시적으로
  요청하지 않는 한 열지 않는다.

## 12. 하지 말 것
